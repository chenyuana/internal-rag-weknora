- 本文所有数值均来自本机实测（SQL / 应用日志 / 接口返回），复现方法见附录 A

## 1. 结论（TL;DR）

用户的直觉「搜索对编号不敏感」方向正确，但**准确位置不是"检索不到编号"，而是"编号只被关键词通道看见，而关键词通道在融合与截断阶段被结构性压制"**。

四层事实：

1. **分词把编号拆碎**：`chinese_lindera` 把 `AC 25.773-1` 切成 `ac | 25 | . | 773 | - | 1`。
2. **关键词通道其实排到了第 1**：`content ||| query`（ParadeDB，OR 语义）命中全库 48022/48022 个块，随后按 BM25 排序，目标文档封面块排第 4、正文块排第 1。
3. **融合把关键词证据压死**：RRF `score = w_v/(k+r_v) + w_k/(k+r_k)`，默认/现网 `w_v=0.7, w_k=0.3, k=60`。纯关键词命中的分数上限是 `0.3/(60+1)`，而向量通道前 50 名的分数是 `0.7/(60+1) … 0.7/(60+50)`，**全部高于它**；`top_k=30` 截断后，关键词证据一条都进不了模型。
4. **向量通道补不上**：目标封面块与问句的余弦只有 **0.354**，落在向量前 50 名之外（0.6B 的 embedding 区分不了 `25.773-1` 与 `25.795-8`）；同时 `rerank_model_id` 为空，Rerank 阶段是空转（日志 `rerank_model=""`）。

另外，仓库里已有 `pinNamedDocuments`（精确编号锁定）并**已在生产运行**（日志可见 `Pinned 3 passage(s) … [25-31]` 等 20+ 次），但它对本次故障无效，原因有两个独立缺口：

- **缺口 A（正则）**：`acNumberPattern` 不认带点的编号（`25.773-1`、`25.621-1`、`25.335-1A`、`25.853-1`、`25.807-1`），所以这些题**从未触发锁定**（生产日志中无任何 `[25.773-1]` 类 Pinned 记录）。
- **缺口 B（首页块）**：即使锁定成功，锁定的 3 个块是「在文档内再做一次语义检索」选出来的，**不保证包含封面页**；而"签发日期 / 责任办公室代号"这类事实恰恰只在封面页。证据：014（20-142）、026/027（23-14）、039（25-16）、045（25-8）、049/050（25-28）都出现了 `Pinned 3 passage(s)`，答案仍然是"检索材料中没有封面页 / 无法确认"。

## 2. 证据链

### 2.1 分词

```sql
SELECT tok FROM paradedb.tokenize(paradedb.tokenizer('chinese_lindera'), 'AC 25.773-1的签发日期是什么？');
-- ac | 25 | . | 773 | - | 1 | 的 | 签发日期 | 是 | 什么 | ？
```

`25.773-1` 不是 token，而是一串数字碎片；在"所有文档都叫 AC xxx"的语料里，`25`、`1` 几乎是停用词级的高频词。

### 2.2 关键词通道的排序

```sql
-- 命中规模
SELECT count(*) FROM embeddings e
WHERE e.knowledge_base_id='acdf013d…' AND e.content ||| 'AC 25.773-1的签发日期是什么？';
-- 48022（= 全库块数）

-- 目标文档排位
-- rank 1: AC_25.773-1.pdf chunk 3 (bm25 15.94)
-- rank 4: AC_25.773-1.pdf chunk 0 (bm25 14.26，封面块，含 Date: 1/8/93)
```

结论：`|||` 是 OR，**关键词通道不做过滤，只做全库 BM25 排序**（每次查询排序 4.8 万行，成本和噪声都高）。但它对目标文档的排序是有效的。

### 2.3 融合的算术（核心）

`internal/application/service/knowledgebase_search_fusion.go:84`：

```
rrf = w_v/(k + vector_rank) + w_k/(k + keyword_rank)
```

现网租户配置（`tenants.retrieval_config`）：

```json
{"rrf_k":60, "rrf_vector_weight":0.7, "rrf_keyword_weight":0.3,
 "embedding_top_k":50, "vector_threshold":0.15, "rerank_model_id":""}
```

于是：

| 来源 | 分数 | 归一化后（×61，日志所示口径） |
|---|---|---|
| 关键词第 1 名（仅此一路） | 0.3/61 = 0.004918 | **0.300** |
| 向量第 1 名 | 0.7/61 = 0.011475 | 0.700 |
| 向量第 50 名 | 0.7/110 = 0.006364 | **0.388** |

**推论：只要向量通道召回满 50 条，任何"只在关键词里出现"的块，分数必然低于全部向量命中；`top_k=30` 一截，关键词证据全灭。**

实测 Q001（`AC 25.773-1 的签发日期？`）的管线日志：

```
FilterTopK action=input merge_cnt=21 rerank_cnt=0 search_cnt=26 top_k=30
→ 最终进入上下文的 21 个块中，AC_25.773-1.pdf 出现 0 次
```

并且向量通道 50 条里没有目标块（余弦 0.354，阈值 0.15 不是问题，是排名问题）。

### 2.4 Rerank 空转

`rerank_model_id: ""`、日志 `stage=Rerank action=input candidate_cnt=26 rerank_model=""` —— 没有交叉编码器按字面重合度重排，最后一道可能的补救不存在。

### 2.5 已有锁定机制的两个缺口

生产日志（节选）：

```
Pinned 3 passage(s) from 1 document(s) named by the query [25-31]
Pinned 3 passage(s) from 1 document(s) named by the query [23-14]
Pinned 3 passage(s) from 1 document(s) named by the query [25-28]
Pinned 3 passage(s) from 1 document(s) named by the query [20-199]
```

- 出现过的编号：`25-31 / 23-14 / 25-30 / 25-16 / 20-136C / 25-8 / 20-199 / 25-28 / 20-142`
- **从未出现**：`25.773-1 / 25.621-1 / 25.335-1A / 25.853-1 / 25.807-1`（全部是带点编号）

对现有正则的验证（`knowledgebase_search_exact.go:60`）：

```go
var acNumberPattern = regexp.MustCompile(
    `(?i)\bAC[\s_\-]*(\d{1,3})\s*-\s*(\d{1,4})\s*([A-Z]?)(?:[^0-9A-Za-z]|$)`)
```

`AC 25.773-1` 在 `AC` 之后是 `25`，紧接着是 `.773`，不满足 `\s*-\s*`（要求数字后直接连字符），**匹配失败 → 整条锁定逻辑不执行**。

即使匹配成功的编号（如 25-28），锁定也只是"在文档内再做一次语义检索取 3 块"。对"签发日期 / 责任办公室代号"这类**封面事实**，这 3 块经常不含 chunk 0，于是答案仍是"没有封面页"：

| 题 | 编号 | 是否 Pinned | 答案 |
|---|---|---|---|
| 026/027 | 23-14 | 是 | "内容仅为正文第 6～8 节及附录 1，未包含封面页" |
| 049/050 | 25-28 | 是 | "仅为附录 A（表 A-1/A-2）" |
| 045 | 25-8 | 是 | "无法确认责任办公室代号" |
| 039 | 25-16 | 是 | "没有出现 DO-160" |

对照：022/023（25-31）、033/034（25-30）、035/036（25-16）、040-043（20-136C）、046/048（20-199）同样被 Pinned，但答案正确 —— 说明**锁定+融合链路本身是通的，缺的是"锁到正确的块"**。

### 2.6 配置级验证（已做，已还原）

把租户权重临时改为 `vector 0.55 / keyword 0.45`，同两题原样重问：

| 题 | 修复前 | 修复后 | 标准答案 |
|---|---|---|---|
| 001 | "资料中没有 AC 25.773-1" | "签发日期 **1993-01-08**（Date: 1/8/93）"，引用 AC_25.773-1.pdf chunk 0 | 1993-01-08 ✅ |
| 017 | "无法确定" | "**2014-10-06**（10/06/14）"，引用 AC_25.621-1.pdf | 2014-10-06 ✅ |

配置已还原为 0.7/0.3（备份见附录 A）。

## 3. 改动方案（按优先级）

### P0 配置层：调整 RRF 权重（无需重新编译，可立即生效、可立即回滚）

```sql
UPDATE tenants
SET retrieval_config = jsonb_set(
      jsonb_set(retrieval_config::jsonb, '{rrf_keyword_weight}', '0.45'),
      '{rrf_vector_weight}', '0.55')
WHERE id = 10000;
```

- 依据：`0.45/(60+1)=0.00738` > 向量第 50 名 `0.55/110=0.005`，关键词头名可稳定进入前 30；实测 001/017 由错转对。
- 风险：BM25 噪声（`|||` 全库命中，头名可能是同数字的邻近文档）一起被抬上来；需要全量 50 题 A/B 验证。
- 适用范围：仅挡"编号唯一命中"这类问题，不解决"锁到错误块"（缺口 B）。

### P1 正则层：让带点编号可被识别（`knowledgebase_search_exact.go`）

```diff
-var acNumberPattern = regexp.MustCompile(
-    `(?i)\bAC[\s_\-]*(\d{1,3})\s*-\s*(\d{1,4})\s*([A-Z]?)(?:[^0-9A-Za-z]|$)`)
+// 编号本体允许 NNN / N.NNN 两种写法，允许尾部的 -数字 段与修订字母：
+//   AC 25-31 / AC 20-136C / AC 25.773-1 / AC 25.335-1A / AC 25.853-1
+// 尾段用「非字母数字或文本结束」收口，避免 25.773-1 误吞 25.773-10。
+var acNumberPattern = regexp.MustCompile(
+    `(?i)\bAC[\s_\-]*(\d{1,3}(?:\.\d{1,4})?)\s*-\s*(\d{1,4})((?:-[0-9]{1,2})?)([A-Z]?)(?:[^0-9A-Za-z]|$)`)
```

对应的归一化函数一并调整（把 `25.773-1`、`25.335-1A` 还原成文档名里的同一字符串），并要求：

- `AC 25.773-1` 与 `AC 25.773-1A` 必须解析为**不同**的编号（不得互相锁定）；
- `AC 25.773-10` 不得被读成 `25.773-1`；
- 现有 `AC 20-27G / AC 20-138D_part01…` 行为不变（回滚保护）。

> 注：交接文档 `HANDOFF-20261028-103600.md` 第 33 行已描述过同类改动（"第一编号分组支持可选点号和后续数字"），本节是在 0.8.0 工作区（HEAD `3f930ab7`）上给出的等价补丁，供并线时对齐。

### P2 首页块层：事实类问题强制锁定封面页

对"签发日期 / 发布日期 / 责任办公室 / Initiated by / Subject / 修订"等**文档头事实**问句，在锁定文档后除语义 3 块外，**强制加入 `chunk_index = 0`（或 `metadata.page_start = 1`）的块**：

```go
// 伪代码，插入 pinNamedDocuments 的 chunks 组装处
chunks := s.namedDocumentChunks(ctx, document, params)     // 现有：语义 3 块
if isDocumentHeaderQuestion(params.OriginalQuery) {
    header := s.firstChunkOf(ctx, document)                // chunk_index=0 / page_start=1，text 类型，enabled
    if header != nil && !containsID(chunks, header.ChunkID) {
        chunks = append([]*types.IndexWithScore{header}, chunks...)
    }
}
```

依据：2.5 表格里 8 道"已 Pinned 但答不出"的题全部属于封面事实。

### P3 截断层：保证锁定块不被 FilterTopK 再排掉

`internal/application/service/chat_pipeline/filter_top_k.go:41` 会**按分数重排后再截断**：

```go
filterTopK := func(searchResult []*types.SearchResult, topK int) []*types.SearchResult {
    sortSearchResultsDeterministically(searchResult)
    if topK > 0 && len(searchResult) > topK { searchResult = searchResult[:topK] }
    return searchResult
}
```

`promoteNamedChunks` 只把锁定块放到候选列表**前面**，一旦下游按分数重排，它们仍会掉出去（当前没掉是因为子检索返回的 RRF 分较高，属于"碰巧成立"，不是保证）。建议二选一：

- **A（推荐）**：`types.SearchResult` 增加 `Pinned bool`，`sortSearchResultsDeterministically` 把 Pinned 稳定排在前面，且 `topK` 截断前先扣除 Pinned 数量（保证 Pinned 必进且不挤爆预算）；
- **B（最小改动）**：在 `HybridSearch` 返回前给锁定块 `Score = max(候选最高分) + ε`。

### P4 索引/模型层（长期，不在本次）

- 分词保留标识符：给 `embeddings.content` 增加一份"标识符归一化"字段或 ngram 索引，让 `25.773-1` 成为一个 token；
- `|||`（OR）在全库语料下等价于"全表 BM25"，建议改为构造布尔查询（内容词 AND、编号整体匹配），既降噪也降成本；
- 配置 rerank 模型（`rerank_model_id`），让 Rerank 阶段真正生效。

docker logs --tail 5000 WeKnora-app 2>&1 | grep -E 'stage=(Rerank|FilterTopK|IntoChatMessage)'
